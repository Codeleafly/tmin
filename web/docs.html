tmin v{{version}} · self-hosted tunneling — server + CLI in one small package.

Getting started

Run your own server (see deployment), then:

tmin config set server https://tunnel.example.com
tmin http 3000 --anonymous   # instant short-lived link (default {{anonTtlMinutes}} min)
tmin login                   # browser device flow — approve with a code
tmin http 3000               # permanent {{baseUrl}}/<you>

Architecture

One Node process serves the REST API, the WebSocket control plane (/tunnel), the public gateway and the web UI. The CLI dials out; public traffic rides that socket — the server never dials into your network. Live reachability lives in memory; route ownership lives in the JSON store (migrated, atomically written).

Installation

git clone <repo> && cd tmin
npm install            # only dependency: ws
npm run build && npm start

Requires Node 20+. No database server needed for single-server mode.

CLI installation

npm install
npm i -g .
tmin --help

# no global install? run from the repo:
npm run cli -- --help

Registration and login

Register on the web UI at /register or via POST /api/v1/auth/register. Usernames are lowercase-unique, 3–32 chars, a-z 0-9 - _, with system names reserved (api admin dashboard docs login …). Browser login sets an HttpOnly tmin_sid cookie; the CLI uses revocable bearer tokens.

CLI login — OAuth-style device flow

tmin login uses a device-authorization flow (RFC 8628-style):

  1. The CLI requests a device code and prints a short user code plus the URL /device.
  2. You open the URL in any browser (phone or computer) and enter the code — log in first if needed.
  3. You see which device asked and Approve or Deny.
  4. The CLI polls the server, receives a revocable tmin_… bearer token and stores it with 0600 permissions.

Prefer a token you generated yourself? Two more methods:

tmin login --token <secret>   # paste an API token (from the dashboard)
tmin login --password         # classic username/password prompt

Codes expire after 10 minutes, are one-time-use, and every approve/deny is audit-logged. Approving creates a normal API token that you can revoke anytime in the dashboard.

API tokens

Generate tokens in the dashboard (name + optional expiry; the secret is shown once) or from the CLI:

tmin token create --name laptop   # secret printed ONCE
tmin token list
tmin token revoke <id>

Tokens are SHA-256 hashed at rest with last-used stamps and instant revocation. Never put tokens in URLs or shell history.

Anonymous tunnels

tmin http 3000 --anonymous returns /a-xxxxxx. The server sets expiry = start + ANONYMOUS_TUNNEL_TTL_SECONDS (default 1800s); reconnecting with the resume token rejoins the same session without extending it. Offline anonymous paths show the offline page (502); expired ones return 410. Per-IP concurrency and body-size caps apply.

Named URLs

Your account owns {{baseUrl}}/<username> permanently. The route stays yours while offline (visitors see a friendly offline page); it never forwards to anyone else. Rename policy: only admins can rename, only with no live tunnels, fully audit-logged.

Multiple tunnels and route slots

tmin http 3000          # → /you
tmin http 8080 --slot 2   # → /you/2
tmin http 5000 --slot 3   # → /you/3

Allocation is transactional — concurrent connects can never double-book a slot. Max 3 live tunnels on the free plan (server-enforced, TUNNEL_LIMIT_REACHED).

HTTP and WebSocket forwarding

GET/POST/PUT/PATCH/DELETE/HEAD/OPTIONS, query strings, headers, cookies, redirects and streaming bodies are proxied. Bodies stream in 48 KB chunks with backpressure — nothing unbounded is buffered. WebSocket upgrades are bridged bidirectionally with frame-size and lifetime caps. Timeouts (30s default), cancellation and quota-exhausted-mid-stream all return explicit errors.

Authentication

Browsers: HttpOnly + SameSite=Lax cookies, 7-day expiry, per-session revocation. CLI/API: tmin_… bearer tokens, SHA-256 hashed at rest, optional expiry, last-used stamps, instant revocation. Passwords: scrypt (memory-hard, Node builtin). Reset tokens are single-use, 1-hour, and revoke all sessions. Auth endpoints are rate-limited with generic login failures.

REST API reference

Versioned under /api/v1. Machine-readable spec at /openapi.json (generated from the route table; CI checks sync). Errors are {error:{code,message},requestId} with stable codes. Example:

curl -H "Authorization: Bearer <token>" {{baseUrl}}/api/v1/me

Upload and download quotas

Convention: upload = public→local request bytes; download = local→public response bytes. Defaults: 1 GB/day each (FREE_*_LIMIT_BYTES). Usage aggregates flush every 5s and survive restarts. Dashboards warn at 80%. Admins are uncapped. Exhaustion stops traffic with QUOTA_EXCEEDED_*, never silently.

Access protection

Planned per-route policies (basic-auth / bearer / IP allowlist / share tokens) are not yet enforced — all routes are currently public. Do not rely on URL secrecy for sensitive apps.

Custom domains

Planned, not implemented. Path routing (/username) is the supported mode. Custom domains need DNS verification + per-domain TLS.

Environment variables

See .env.example — every knob is documented there (domain, secrets, TTLs, quotas, protocol limits, rate limits, retention, maintenance).

Self-hosted deployment

git clone <repo> && cd tmin
npm ci --omit=dev && npm run build
SESSION_SECRET=… ADMIN_PASSWORD=… DATA_DIR=/var/lib/tmin npm start

Single-server mode: one Node process, no database server. Run it under systemd (or any supervisor) — Restart=always, EnvironmentFile=/etc/tmin.env. Back up data/tmin.json (all durable state).

TLS and DNS

Point A tunnel.example.com → server IP. Run Caddy in front (example config: deployment/Caddyfile) — it obtains and renews Let's Encrypt certificates automatically and proxies HTTP+WebSocket to the app. Only trust X-Forwarded-For when TRUST_PROXY=true behind that proxy.

Administration

Admins manage users, renames, quotas, tunnels, anonymous sessions, audit logs, maintenance mode and server health from /admin. Every privileged action is audit-logged with actor, target and result.

How to log in as admin (web)

  1. Set ADMIN_USERNAME and ADMIN_PASSWORD (plus optional ADMIN_EMAIL) in the server environment before the first start.
  2. Start the server — the admin account is created once, from the environment.
  3. Open /login and sign in with those credentials. You are redirected to the dashboard; /admin unlocks automatically.

Restarts never overwrite an existing admin password. Changing ADMIN_PASSWORD later has no effect on a running database — use "Reset PW" on the admin page or delete the DB row intentionally.

Web dashboard

Static, mobile-responsive pages (system fonts + Tailwind via CDN, no build step) served by the same process:

  • /dashboard — tunnels, routes, usage, API token generation, sessions, password change.
  • /admin — users, live tunnels, anonymous sessions, quotas, audit log, maintenance.
  • /device — approve tmin login requests (device flow).

Security

Threat model, boundaries and controls: see SECURITY.md. Highlights: server-authoritative everything, segment-aware routing (no prefix capture), bounded buffers, fail-closed quota/auth, secret redaction, no stack traces in prod. Device codes are hashed at rest, single-use and expire in 10 minutes.

Troubleshooting

tmin doctor     # DNS, TLS, auth, version checks
tmin status     # connection, URL, usage
tmin usage --json

Common: TUNNEL_LIMIT_REACHED → stop a tunnel; QUOTA_EXCEEDED_* → daily bandwidth cap reached; ANON_EXPIRED → anonymous links expire by design; AUTHORIZATION_PENDING → approve the CLI code in the browser; DEVICE_CODE_EXPIRED → run tmin login again. If a named path shows the offline page, (re)start your CLI.

Operational monitoring

GET /health (public), GET /ready (db check), GET /api/v1/admin/metrics (live tunnels, latency, error rate, bytes). Structured JSON logs with request correlation IDs.

FAQ

Does my URL change on reconnect? No — registered URLs are permanent.
Can someone steal my offline route? No — ownership is per-account in the database.
Is there a login page? Yes — /login. Registration creates accounts; the admin uses the env-bootstrapped credentials above.
Why scrypt instead of argon2? Zero native deps keeps installs tiny and reproducible; still memory-hard.
Horizontal scaling? Not with the embedded store — single-server mode is supported; multi-instance needs Postgres (planned).
